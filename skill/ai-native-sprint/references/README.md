# 迭代管理文档仓库

本目录使用 [Schemark](https://github.com/charlesvhe/schemark) 管理迭代（Sprint）的目录结构、文件命名与内容规范。所有约束定义在 `schemark.json` 中，可通过 `schemark valid` 命令自动校验。

---

## 目录结构

```
docs/sprint/
├── schemark.json                          # 规则定义
├── README.md                              # 本文件
├── <sprint 目录>/                          # 进行中或已结束的迭代
│   ├── assets/                            # markdown需要引用的其他文件，例如 图片、视频等
│   ├── README.md                          # 迭代说明（必须）
│   ├── T0001-xxx.md                       # 任务
│   └── B0001-xxx.md                       # 缺陷
└── archive/                               # 已归档迭代
    └── <sprint 目录>/                      # 结构与上层一致
```

### Sprint 目录命名

**格式**：`<开始日期>-<结束日期>-<版本号>-<迭代名称>`

| 片段 | 含义 | 示例 |
| --- | --- | --- |
| 开始日期 | 迭代计划开始（yyyyMMdd） | `20260201` |
| 结束日期 | 迭代计划结束（yyyyMMdd） | `20260228` |
| 版本号 | 迭代版本 | `v1.0` |
| 迭代名称 | 自由文本 | `支付与订单` |

完整示例：`20260201-20260228-v1.0-支付与订单`

### archive 目录

固定名称 `archive`，内部子目录遵循相同的 Sprint 命名规则，表示已归档的迭代。

## 迭代说明（README.md）

每个 Sprint 目录下**必须**包含一个 `README.md`。

### Frontmatter

| 字段 | 类型 | 必填 | 说明 |
| --- | --- | --- | --- |
| 迭代场景 | string | 否 | 枚举：`缺陷修复` / `简单需求` / `标准需求` / `复杂需求` |
| 迭代负责人 | string | **是** | 格式：`姓名 域账号`，必须出自 `团队成员` |
| 产品负责人 | string | **是** | 格式同上，必须出自 `团队成员` |
| 测试负责人 | string | **是** | 格式同上，必须出自 `团队成员` |
| 实际结束时间 | string | 否 | 日期格式 `yyyy-MM-dd` |
| 团队成员 | array | **是** | 本迭代涉及的所有人员名册，每条 `姓名 / 域账号 / 角色`，至少 1 条；后续任务/缺陷/迭代各人员字段必须从此列表中选择，避免笔误 |

> **设计取舍**：所有人员（迭代负责人、产品负责人、测试负责人、任务负责人、缺陷提出/处理/引起人、提测人、变更人、验收人、知识库回填负责人、篝火评审人员、迭代范围责任开发）都必须出现在迭代 README 的 `团队成员` 中。新增人员要先追加到 `团队成员`，再写到对应字段，保证全迭代的姓名+域账号拼写来自同一份名册。

### Body 必须包含的章节

校验仅检查章节标题存在，不限制顺序，允许包含额外章节。

| 章节 | 说明 |
| --- | --- |
| `## 篝火评审` | 多角色（PM/UED/DEV/QA）评审人员与评审报告，由 `ai-native-campfire` skill 生成后回填 |
| `## 迭代范围` | 本迭代包含的需求与责任人 |
| `## 提测计划` | 各轮次提测安排，包含计划与实际提测时间、提测说明 |
| `## 测试用例` | 各测试用例文件的执行人、执行结果与关联缺陷 |
| `## 变更记录` | 迭代过程中的范围或计划变更 |
| `## 知识库回填` | 迭代结束后的知识沉淀跟踪 |
| `## 验收发布` | 产品验收结论与发布产物记录 |

```markdown
# 高并发下重复创建订单

## 重现步骤

[操作步骤] 压测脚本以同一 `Idempotency-Key` 并发发送 100 次创建订单请求。
[现象] 同一幂等键仍创建出 3 条订单。
[期待结果] 同一 `Idempotency-Key` 在并发场景下只应产生 1 条订单。

## 修复细节

根因：幂等键写入未放在事务起始，存在 race condition。

修复：将 `Idempotency-Key → order_id` 的映射改为唯一索引落库后，再进入下游订单创建逻辑，保证并发请求只能有一条成功落库。
```

## 典型工作流程示例

下面以一个完整的迭代为例，演示从迭代启动到验收发布的关键节点对应的文件操作。所有动作都通过**新建/修改 Markdown 文件**完成，配合 Git 提交即可天然形成审计轨迹。

### 1. 篝火评审

迭代规划完成、即将拆解任务前，**先**调用 `ai-native-campfire` skill 对本迭代关联的 OpenSpec specs / User Story 进行多角色评审，输出按角色分组的报告。报告内容会在下一步「新建迭代」时直接写入 README 的 `## 篝火评审` 章节。

```markdown
## 篝火评审

评审人员：林菲 linfei（PM）、苏婷 suting（UED）、王浩 wanghao（DEV）、刘洋 liuyang（DEV）、赵琳 zhaolin（QA）
评审报告内容：
- PM：<!-- 通过项 / 待补充项 / 建议修改项 -->
- UED：...
- DEV：...
- QA：...
```

> **设计取舍**：评审报告以摘要形式回填，按角色分组，便于后续追溯共识；详细修正建议由各角色直接落到 spec 或 US 文档，不堆在迭代 README 里。
>
> **顺序约束**：篝火评审是迭代启动的**前置**动作。如果当前会话还没有进行篝火评审，应该先做评审，或在「新建迭代」时以交互方式收集评审人员和报告内容，再写入 README——绝不允许把 `## 篝火评审` 留成 TODO 占位。

### 6. 缺陷流转

缺陷的生命周期通过修改自身 frontmatter 推进，**不影响任务状态**：

| 阶段 | 操作 | 关键字段变化 |
| --- | --- | --- |
| 开发修复 | 开发更新缺陷文件 | `状态: 待修复 → 待验证`，补充 `解决版本`、`解决方法: 已修复`，正文写入根因与修复方案 |
| 测试验证通过 | 测试更新缺陷文件 | `状态: 待验证 → 待修复` 之外的终态由团队约定（例如归档前留在 `待验证`，或扩展枚举增加终态） |
| 验证不通过 | 测试更新缺陷文件 | 补充 `不通过版本`，状态回到 `待修复` |
| 误报或设计如此 | 测试或产品更新缺陷文件 | `状态: 拒绝`，补充 `打回原因` |

`B0009-弹窗文案不一致.md` 是一个被打回的真实示例，可作参考。

### 7. 验收发布

所有任务完成、缺陷收敛后，产品验收。**验收人只修改迭代 README 的 `## 验收发布` 章节**：

```diff
 ## 验收发布

-验收结论：[ ] 通过 / [ ] 不通过
-验收人：
-发布产物（制品仓库地址或制品版本号）：
```

如验收不通过、需要返工，验收人在 `## 变更记录` 追加一行说明范围/工期影响，然后开新任务或重开缺陷处理。
