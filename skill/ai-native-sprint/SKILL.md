# AI Native Sprint - 迭代管理技能

本技能帮助用户在基于 Schemark 规范的项目中管理软件开发迭代、任务和缺陷。

## 核心功能

1. **创建迭代（Sprint）** - 创建符合命名规范的迭代目录和README.md
2. **创建任务（Task）** - 在迭代中创建T文件
3. **创建缺陷（Bug）** - 在迭代中创建B文件
4. **状态流转** - 更新任务/缺陷的状态字段
5. **归档迭代** - 将完成的迭代移动到archive目录
6. **校验** - 运行schemark命令进行结构校验

## 工作流程

### 步骤1：理解用户意图

用户可能会用以下方式表达需求：

- **直接命令式**："创建一个新迭代"、"添加一个任务"、"把这个bug标记为已修复"
- **描述式**："我们要开始v2.0的开发了"、"测试发现了一个支付的问题"

你需要识别用户想要执行的操作类型，并收集必要信息。

### 步骤2：定位项目根目录

自动查找 `schemark.json` 文件来确定项目根目录。这是schemark项目的标识文件。

**查找策略**：

1. 首先检查当前工作目录
2. 向上查找父目录（最多3层）
3. 向下查找子目录（最多3层）

使用辅助脚本自动定位：

```bash
# 自动查找schemark.json所在目录
python3 scripts/find_schemark.py . 3
```

脚本会返回schemark.json所在的目录路径。如果在3层范围内找不到，再询问用户项目根目录位置。

**示例场景**：

- 用户在 `/project/example/sprint1/` 目录下 → 自动找到 `/project/example/`
- 用户在 `/project/` 目录下 → 自动找到 `/project/example/`
- 用户在 `/project/docs/` 目录下 → 自动找到 `/project/example/`

### 步骤3：检查schemark命令

在执行任何操作前，检查schemark命令是否可用。如果不存在，自动使用npm全局安装。

**检查和安装流程**：

```bash
# 检查schemark命令是否存在
if ! command -v schemark &> /dev/null; then
    echo "schemark命令未找到，正在安装..."
    npm install -g schemark
fi

# 验证安装成功
schemark -h
```

**注意事项**：
- 需要Node.js (>=18) 和npm环境
- 全局安装可能需要适当的权限（sudo或管理员）
- 安装完成后会自动继续执行操作

### 步骤4：执行对应操作

根据用户意图执行相应操作。

## 操作详解

### 创建迭代（Sprint）

**命名规范**：`<开始日期>-<结束日期>-<版本号>-<迭代名称>`

- 开始日期：yyyyMMdd格式，如 `20260201`
- 结束日期：yyyyMMdd格式，如 `20260228`
- 版本号：如 `v1.0`、`v2.0`
- 迭代名称：自由文本，如 `支付与订单`

**需要收集的信息**：

1. 迭代名称
2. 计划开始日期（yyyyMMdd）
3. 计划结束日期（yyyyMMdd）
4. 版本号
5. 迭代负责人（格式：姓名 域账号）
6. 产品负责人（格式：姓名 域账号）
7. 测试负责人（格式：姓名 域账号）
8. 实际结束时间（yyyy-MM-dd格式）
9. 迭代场景（可选）：缺陷修复/简单需求/标准需求/复杂需求

**执行步骤**：

1. 构造目录名：`{开始日期}-{结束日期}-{版本号}-{迭代名称}`
2. 创建目录和assets子目录
3. 创建README.md，包含：
   - Frontmatter（必填字段）
   - 迭代目标、关键依赖、风险等自由内容
   - 必须包含的章节：迭代范围、提测计划、知识库回填、变更记录

**README.md模板**：

```markdown
---
迭代场景: 标准需求
迭代负责人: {姓名} {域账号}
产品负责人: {姓名} {域账号}
测试负责人: {姓名} {域账号}
实际结束时间: {yyyy-MM-dd}
---

# {迭代名称}

{迭代描述}

- {目标1}
- {目标2}

- {依赖描述}

## 风险

- {风险描述}

## 迭代范围

| PRD/OpenSpec | 名称 | 责任开发 |
| --- | --- | --- |
| <!-- PRD/OpenSpec 相对路径 --> | xxx | <!-- 姓名+域账号 例如：张三 zhangsan --> |

## 提测计划

| 轮次 | 提测范围 | 计划提测时间 | 提测人 |
| --- | --- | --- | --- |
```

### 创建任务（Task）

**文件命名规范**：`T<4位编号>-<标题>.md`

**编号分配策略**：在当前sprint目录内递增

1. 扫描当前sprint目录下所有T开头的文件
2. 提取最大编号（如T0006）
3. 新编号为最大编号+1（如T0007）
4. 如果没有现有任务，从T0001开始

**需要收集的信息**：

1. 任务标题
2. 负责人（格式：姓名 域账号）
3. 预估工时（小时，≥0）
4. 已投入工时（小时，≥0，通常初始为0）
5. 状态：进行中/完成/取消
6. 标签（可选）：字符串数组
7. 关联内容（可选）：PRD或OpenSpec的相对路径数组

**文件模板**：

```markdown
---
负责人: {姓名} {域账号}
预估工时: {数字}
已投入工时: {数字}
状态: 进行中
标签:
  - {标签1}
  - {标签2}
关联内容:
  - {相对路径}
---

# {任务标题}

{任务描述}

## {自定义章节}

{内容}
```

**执行步骤**：

1. 确定当前sprint目录
2. 扫描现有T文件，计算下一个编号
3. 构造文件名：`T{编号}-{标题}.md`
4. 创建文件，填充frontmatter和基本内容

### 创建缺陷（Bug）

**文件命名规范**：`B<4位编号>-<标题>.md`

**编号分配策略**：在当前sprint目录内递增（与Task相同逻辑）

**需要收集的信息**：

1. 缺陷标题
2. 优先级：紧急/高/中/低
3. 严重性：致命/严重/一般/细微
4. 提出人（格式：姓名 域账号）
5. 处理人（格式：姓名 域账号）
6. 状态：待修复/待验证/拒绝/挂起
7. 引起人（可选）
8. 缺陷起因（可选）：编码/研发设计/测试/需求/交互视觉设计/资源或效果/部署/文档问题/安全问题/建议/其他
9. 解决方法（可选）：已修复/延迟解决/不计划修复/临时解决/已知问题/误报问题/无法修复/部署问题/不再是问题/无法复现
10. 打回原因（可选）：误报的问题/设计如此/需要更多信息/重复提交
11. 解决版本（可选）
12. 不通过版本（可选）
13. 重开版本（可选）

**文件模板**：

```markdown
---
优先级: {紧急/高/中/低}
严重性: {致命/严重/一般/细微}
提出人: {姓名} {域账号}
处理人: {姓名} {域账号}
状态: 待修复
---

# {缺陷标题}

## 重现步骤

[操作步骤] {步骤描述}
[现象] {实际现象}
[期待结果] {期待结果}

## 修复细节

{修复细节描述}
```

**执行步骤**：

1. 确定当前sprint目录
2. 扫描现有B文件，计算下一个编号
3. 构造文件名：`B{编号}-{标题}.md`
4. 创建文件，填充frontmatter和必须章节

### 状态流转

更新任务或缺陷的状态字段。

**任务状态流转**：
- 进行中 → 完成
- 进行中 → 取消
- 完成 → 进行中（重新打开）

**缺陷状态流转**：
- 待修复 → 待验证
- 待验证 → 待修复（验证不通过）
- 待修复 → 拒绝
- 待修复 → 挂起
- 挂起 → 待修复

**执行步骤**：

1. 读取目标文件
2. 解析frontmatter
3. 更新状态字段
4. 如果是缺陷状态变更，可能需要同时更新其他字段：
   - 待修复 → 待验证：可能需要填写"解决方法"和"解决版本"
   - 待验证 → 待修复：可能需要填写"不通过版本"
   - 拒绝：可能需要填写"打回原因"
5. 写回文件

### 归档迭代

将完成的迭代移动到archive目录。

**前置条件检查**：

1. 迭代目录存在
2. 迭代README.md中的"实际结束时间"已填写
3. 建议检查迭代内的任务和缺陷是否都已完成/关闭

**执行步骤**：

1. 确认archive目录存在，不存在则创建
2. 使用`mv`命令移动整个迭代目录到archive下
3. 保持目录名不变

```bash
# 示例
mv 20260201-20260228-v1.0-支付与订单 archive/
```

### 校验

运行schemark命令进行结构校验。

**执行时机**：每次创建或修改操作后自动执行

**命令**：

```bash
# 在项目根目录执行
schemark valid .
```

**处理结果**：

- 如果校验通过，简单告知用户
- 如果校验失败，展示错误信息并提示用户修复

## 辅助功能

### 自动发现项目根目录

使用 `find_schemark.py` 脚本自动定位schemark.json文件：

```bash
python3 scripts/find_schemark.py <start_dir> [max_depth]
```

**查找逻辑**：

1. 检查当前目录是否有schemark.json
2. 向上查找父目录（最多3层）
3. 向下查找子目录（最多3层）

**返回值**：

- 成功：输出schemark.json所在目录的绝对路径
- 失败：输出错误信息到stderr，退出码1

**使用场景**：

- 用户在sprint子目录中执行操作 → 自动找到项目根目录
- 用户在项目的任意子目录中 → 自动定位到正确位置
- 避免用户手动指定路径

### 查找当前Sprint

如果用户没有明确指定sprint，需要智能判断：

1. 检查当前工作目录是否在某个sprint目录内
2. 如果在项目根目录，使用 `find_sprints.py` 列出所有非archive的sprint目录，选择最新的（按开始日期排序）
3. 询问用户确认

### 编号冲突处理

如果计算出的编号已存在（不应该发生，但需要防御）：

1. 继续递增直到找到可用编号
2. 警告用户可能存在编号不连续的情况

### 日期格式转换

用户可能用自然语言描述日期，需要转换为规范格式：

- "明天" → 计算具体日期
- "下周一" → 计算具体日期
- "2026年2月1日" → 20260201
- "2026-02-01" → 20260201

### 人员信息格式

确保人员信息符合"姓名 域账号"格式：

- 如果用户只提供姓名，提示需要域账号
- 如果格式不对，提示正确格式

## 错误处理

1. **找不到schemark.json**：
   - 首先使用 `find_schemark.py` 在当前目录及其父子目录（3层范围内）自动查找
   - 如果仍未找到，提示用户这不是一个schemark项目，询问项目根目录
   - 建议用户检查是否在正确的项目目录中

2. **sprint目录不存在**：提示用户指定的sprint不存在，使用 `find_sprints.py` 列出可用的sprint

3. **必填字段缺失**：明确告知缺少哪些字段，引导用户补充

4. **校验失败**：展示schemark的错误信息，帮助用户理解并修复

## 注意事项

1. **严格遵守schemark.json规范**：所有创建的文件和目录必须符合规范
2. **保持文件格式一致**：frontmatter使用YAML格式，body使用Markdown
3. **编号连续性**：尽量保持T/B编号连续，避免跳号
4. **日期格式统一**：目录名用yyyyMMdd，frontmatter中的日期用yyyy-MM-dd
5. **人员信息格式**：始终使用"姓名 域账号"格式
6. **必须章节**：确保README.md和B文件包含所有必须的章节
7. **校验反馈**：每次操作后运行校验，及时发现问题
8. **用户确认**：对于重要操作（如归档），在执行前确认用户意图

## 技能边界

本技能**不负责**：

- 修改schemark.json规则定义
- 编辑任务/缺陷的详细内容（只负责创建和状态流转）
- 生成复杂的项目报告
- 与外部系统（如Jira、GitLab）集成

这些操作应该由用户或其他专门的技能处理。
