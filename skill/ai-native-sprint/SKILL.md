# AI Native Sprint - 迭代管理技能

本技能在当前代码仓库的 **`docs/sprint/`** 子目录（默认路径，可由用户指定其他路径）中管理软件开发迭代、任务和缺陷。

## 重要边界：不影响仓库根目录

本技能的所有操作仅限于 Sprint工作区目录（默认 `docs/sprint/`）内部：

- **禁止**将 Sprint工作区目录视为独立项目或 Claude Code 工作目录
- Sprint工作区中的 `schemark.json` 是迭代管理的规则定义文件，不是项目配置

## 核心概念

| 术语 | 含义 |
| --- | --- |
| Sprint工作区 | 存放迭代管理文件的目录，默认为 `docs/sprint/`，内含 `schemark.json` |
| 仓库根目录 | 用户的代码仓库根目录（Claude Code 的工作目录），本技能不修改它 |
| schemark.json | Sprint工作区内的规则定义文件，用于校验目录结构 |
| 团队成员 | 迭代 README frontmatter 中的人员名册，本迭代涉及人员的唯一登记处 |

## 人员信息一致性规则（强制）

为避免姓名/域账号笔误，所有出现人员的字段都必须从迭代 README frontmatter 的 `团队成员` 列表中选择，禁止直接输入新人员。

**适用范围**：

- 迭代 README frontmatter：`迭代负责人` / `产品负责人` / `测试负责人`
- 迭代 README body：`## 篝火评审` 评审人员、`## 迭代范围` 责任开发、`## 提测计划` 提测人、`## 变更记录` 变更人、`## 验收发布` 验收人、`## 知识库回填` 负责人
- 任务文件 frontmatter：`负责人`
- 缺陷文件 frontmatter：`提出人` / `处理人` / `引起人`

**操作约束**：

1. 创建迭代时，必须先收集 `团队成员` 名册，再写入 frontmatter。名册必须覆盖后续要在迭代里出现的所有人员。
2. 创建任务/缺陷、回填提测/验收/变更/知识库时，先读取迭代 README 的 `团队成员`，把候选项作为枚举展示给用户，由用户从中选择，再以 `姓名 域账号` 的形式写入字段。
3. 如果用户提到的人不在 `团队成员` 中：
   - 优先确认是否笔误；
   - 如确实是新成员，**先**用追加的方式更新迭代 README frontmatter 的 `团队成员`（保留已有条目，新增一条），再继续后续写入；
   - 不允许在不更新 `团队成员` 的情况下把新人员写到任何字段里。
4. 写入字段后，姓名与域账号的拼写必须与 `团队成员` 中对应条目逐字一致。

## 核心功能

1. **初始化Sprint工作区（Init）** - 在指定子目录初始化迭代管理结构
2. **篝火评审前置（Campfire）** - 创建迭代前先调用 `ai-native-campfire` skill 完成多角色评审；如会话内未做评审，提示先评审或交互式收集摘要
3. **创建迭代（Sprint）** - 创建符合命名规范的迭代目录和README.md，`## 篝火评审` 章节直接填入步骤 2 的报告
4. **创建任务（Task）** - 在迭代中创建T文件
5. **创建缺陷（Bug）** - 在迭代中创建B文件，可关联到引入该缺陷的任务
6. **状态流转** - 更新任务/缺陷的状态字段
7. **提测** - 在迭代README的「提测计划」表回填实际提测时间与提测人（迭代级动作，不修改任务状态）
8. **验收发布** - 在迭代README的「验收发布」章节填写验收结论、验收人、发布产物
9. **归档迭代** - 将完成的迭代移动到archive目录
10. **校验** - 运行schemark命令进行结构校验
11. **分析迭代（Analyze）** - 通过 `schemark meta` 导出结构化JSON，进行迭代数据分析

## 工作流程

### 步骤1：理解用户意图

用户可能会用以下方式表达需求：

- **初始化**："初始化迭代工作区"、"在 docs/sprint 创建迭代管理结构"
- **直接命令式**："创建一个新迭代"、"添加一个任务"、"把这个bug标记为已修复"
- **描述式**："我们要开始v2.0的开发了"、"测试发现了一个支付的问题"

识别用户想要执行的操作类型，并收集必要信息。

### 步骤2：定位Sprint工作区

自动查找 `schemark.json` 文件来确定Sprint工作区位置。`schemark.json` 是Sprint工作区的标识文件（不是仓库配置文件）。

**默认位置**：`<仓库根目录>/docs/sprint/`

**查找策略**：

1. 首先检查默认位置 `docs/sprint/schemark.json`
2. 在当前工作目录附近查找（向上/向下最多3层）

使用辅助脚本自动定位：

```bash
python3 scripts/find_schemark.py docs/sprint 3
```

脚本返回 `schemark.json` 所在目录的路径。如果找不到，询问用户Sprint工作区位置或建议初始化。

### 步骤3：检查schemark命令

在执行任何操作前，检查schemark命令是否可用：

```bash
if ! command -v schemark &> /dev/null; then
    echo "schemark命令未找到，正在安装..."
    npm install -g schemark
fi
schemark -h
```

### 步骤4：执行对应操作

根据用户意图在Sprint工作区内执行相应操作。所有文件操作仅限于Sprint工作区目录内部。

## 操作详解

### 初始化Sprint工作区（Init）

在用户代码仓库的子目录中初始化迭代管理结构。默认路径为 `docs/sprint/`。

**需要收集的信息**：

1. 目标子目录路径（默认 `docs/sprint/`，用户可指定其他路径）

**执行步骤**：

1. 确认目标子目录存在（不存在则创建，包括中间目录）
2. 检查目标目录中是否已有 `schemark.json`（如已存在则提示用户，避免覆盖）
3. 从本技能的 `references/` 目录复制文件到目标目录：
   - `references/schemark.json` → `<目标目录>/schemark.json`
   - `references/README.md` → `<目标目录>/README.md`
4. 创建archive子目录 `<目标目录>/archive/`
5. 运行 `schemark valid <目标目录>` 验证初始化结果

**复制命令示例**：

```bash
SKILL_DIR="$(dirname "$(realpath "$0")")"
TARGET_DIR="docs/sprint"

mkdir -p "$TARGET_DIR/archive"
cp "$SKILL_DIR/references/schemark.json" "$TARGET_DIR/schemark.json"
cp "$SKILL_DIR/references/README.md" "$TARGET_DIR/README.md"
```

**注意事项**：

- 如果目标目录已有 schemark.json，必须先确认用户是否要覆盖
- 初始化完成后运行校验确保结构正确
- **绝不在仓库根目录创建 schemark.json 或 .claude/ 文件夹**

### 创建迭代（Sprint）

**命名规范**：`<开始日期>-<结束日期>-<版本号>-<迭代名称>`

- 开始日期：yyyyMMdd格式，如 `20260201`
- 结束日期：yyyyMMdd格式，如 `20260228`
- 版本号：如 `v1.0`、`v2.0`
- 迭代名称：自由文本，如 `支付与订单`

**需要收集的信息**：

1. 迭代名称
2. 计划开始日期（yyyyMMdd）
3. 计划结束日期（yyyyMMdd）
4. 版本号
5. **团队成员名册**（必须）：本迭代涉及的所有人员，每人三项 `姓名 / 域账号 / 角色`，至少 1 人，且必须覆盖后续要写到 frontmatter 的迭代/产品/测试负责人
6. 迭代负责人（从 团队成员 中选择，写为 `姓名 域账号`）
7. 产品负责人（从 团队成员 中选择）
8. 测试负责人（从 团队成员 中选择）
9. 实际结束时间（yyyy-MM-dd格式）
10. 迭代场景（可选）：缺陷修复/简单需求/标准需求/复杂需求
11. **篝火评审报告**：评审人员（必须出自 团队成员 名册）和按角色分组的报告摘要——必须在创建迭代前就绪

**前置检查：篝火评审**

篝火评审是迭代启动的**前置**动作，不是事后回填。创建迭代前，先判断当前会话是否已经完成篝火评审：

1. **会话内已做评审** —— 上文已经调用过 `ai-native-campfire` skill，或上下文中已有按 PM/UED/Backend/Frontend/QA 五角色组织的评审输出：直接把评审人员和报告摘要写入 README 的 `## 篝火评审` 章节。
2. **会话内未做评审** —— 上下文里没有评审输出：必须二选一，**禁止**把 `## 篝火评审` 章节留成 TODO 占位：
   - **优先**：提示用户先调用 `ai-native-campfire` skill 完成评审，再回到本流程创建迭代。这是推荐路径，因为它保证评审过程留痕。
   - **次选（用户明确要跳过评审过程）**：以交互方式向用户收集评审人员名单和按角色的评审摘要（PM、UED、Backend、Frontend、QA 至少各一行），收集完后再写入 README。
3. **真正不适用**（如纯缺陷修复迭代、无 OpenSpec/US 文档）：经用户确认后，章节正文可填入 `本迭代为缺陷修复/无关联需求文档，不适用篝火评审。`，但 `## 篝火评审` 章节**不能删除**（schemark 校验要求章节存在）。

**执行步骤**：

1. 完成上述「前置检查」，确认评审报告内容就绪
2. 在Sprint工作区内构造目录名：`{开始日期}-{结束日期}-{版本号}-{迭代名称}`
3. 创建目录和assets子目录
4. 创建README.md，包含frontmatter和必须章节，`## 篝火评审` 章节直接填入步骤1得到的报告
5. 运行 `schemark valid` 校验

### 创建任务（Task）

**文件命名规范**：`T<4位编号>-<标题>.md`

**编号分配策略**：在当前sprint目录内递增

1. 扫描当前sprint目录下所有T开头的文件
2. 提取最大编号（如T0006）
3. 新编号为最大编号+1（如T0007）
4. 如果没有现有任务，从T0001开始

**需要收集的信息**：

1. 任务标题
2. 负责人（**从迭代 README frontmatter 的 `团队成员` 中选择**，写为 `姓名 域账号`）
3. 预估工时（小时，≥0）
4. 已投入工时（小时，≥0，通常初始为0）
5. 状态：进行中/完成/取消
6. 标签（可选）：字符串数组
7. 关联内容（可选）：PRD或OpenSpec的相对路径数组

**文件模板**：

```markdown
---
负责人: {姓名} {域账号}
预估工时: {数字}
已投入工时: {数字}
状态: 进行中
标签:
  - {标签1}
关联内容:
  - {相对路径}
---

# {任务标题}

{任务描述}
```

**执行步骤**：

1. 确定当前sprint目录（在Sprint工作区内）
2. 扫描现有T文件，计算下一个编号
3. 构造文件名：`T{编号}-{标题}.md`
4. 创建文件，填充frontmatter和基本内容

### 创建缺陷（Bug）

**文件命名规范**：`B<4位编号>-<标题>.md`

**编号分配策略**：在当前sprint目录内递增（与Task相同逻辑）

**需要收集的信息**：

1. 缺陷标题
2. 优先级：紧急/高/中/低
3. 严重性：致命/严重/一般/细微
4. 提出人（**从迭代 README frontmatter 的 `团队成员` 中选择**，写为 `姓名 域账号`）
5. 处理人（**从 `团队成员` 中选择**）
6. 状态：待修复/待验证/拒绝/挂起
7. 关联任务（可选）：引入该缺陷的任务 ID 数组，如 `["T0007"]`，多个用逗号分隔
8. 引起人（可选，**从 `团队成员` 中选择**）
9. 缺陷起因（可选）：编码/研发设计/测试/需求/交互视觉设计/资源或效果/部署/文档问题/安全问题/建议/其他
10. 解决方法（可选）：已修复/延迟解决/不计划修复/临时解决/已知问题/误报问题/无法修复/部署问题/不再是问题/无法复现
11. 打回原因（可选）：误报的问题/设计如此/需要更多信息/重复提交
12. 解决版本（可选）
13. 不通过版本（可选）
14. 重开版本（可选）

**文件模板**：

```markdown
---
优先级: {紧急/高/中/低}
严重性: {致命/严重/一般/细微}
提出人: {姓名} {域账号}
处理人: {姓名} {域账号}
状态: 待修复
关联任务:
  - {T0001}
---

# {缺陷标题}

## 重现步骤

[操作步骤] {步骤描述}
[现象] {实际现象}
[期待结果] {期待结果}

## 修复细节

{修复细节描述}
```

**执行步骤**：

1. 确定当前sprint目录（在Sprint工作区内）
2. 扫描现有B文件，计算下一个编号
3. 构造文件名：`B{编号}-{标题}.md`
4. 创建文件，填充frontmatter和必须章节

### 状态流转

更新任务或缺陷的状态字段。

**任务状态流转**：
- 进行中 → 完成
- 进行中 → 取消
- 完成 → 进行中（重新打开）

> **重要边界**：任务状态只描述「开发本体」的进度。提测、验收都是迭代级动作，不修改任务的 `状态` 字段——具体见下面的「提测」「验收发布」两节。

**缺陷状态流转**：
- 待修复 → 待验证
- 待验证 → 待修复（验证不通过）
- 待修复 → 拒绝
- 待修复 → 挂起
- 挂起 → 待修复

**执行步骤**：

1. 读取Sprint工作区内的目标文件
2. 解析frontmatter
3. 更新状态字段
4. 如果是缺陷状态变更，可能需要同时更新其他字段：
   - 待修复 → 待验证：可能需要填写"解决方法"和"解决版本"
   - 待验证 → 待修复：可能需要填写"不通过版本"
   - 拒绝：可能需要填写"打回原因"
5. 写回文件

### 提测

提测是**迭代级动作**，通过修改迭代 README 的 `## 提测计划` 表格完成，**不修改任务文件**。

**触发场景**：用户提到"T0007 已经提测了"、"第一轮提测完成"、"今天提测订单模块"。

**需要收集的信息**：

1. 迭代目录（如未指定，按"查找当前 Sprint"逻辑确定）
2. 提测轮次（如 1、2；如未指定，默认匹配第一条尚未填写「实际提测时间」的行）
3. 实际提测时间（yyyyMMdd 格式；如未指定，默认今天）
4. 提测人（**从迭代 README frontmatter 的 `团队成员` 中选择**，写为 `姓名 域账号`；如未指定，沿用该行已有值或询问用户）

**执行步骤**：

1. 定位迭代 README.md
2. 在 `## 提测计划` 表格中找到对应轮次的行
3. 回填 `实际提测时间` 与 `提测人` 单元格
4. 写回文件
5. 运行 `schemark valid` 校验

**示例 diff**：

```diff
 | 轮次 | 提测范围 | 计划提测时间 | 实际提测时间 | 提测人 |
 | --- | --- | --- | --- | --- |
-| 1 | 订单创建、查询、关闭主链路 | 20260218 | | 王浩 wanghao |
+| 1 | 订单创建、查询、关闭主链路 | 20260218 | 20260218 | 王浩 wanghao |
```

**注意事项**：

- 不要把任务的 `状态` 改成"完成"——任务是否完成由测试验证 + 验收阶段决定，提测只是开发交付的节点
- 如用户描述了多轮提测，逐行回填，不要合并
- 如提测计划表里没有对应轮次，需要追加新行（询问用户该轮次的「提测范围」「计划提测时间」）

### 验收发布

验收发布是**迭代级动作**，通过修改迭代 README 的 `## 验收发布` 章节完成。

**触发场景**：用户提到"迭代验收通过"、"v1.0 已经发布了"、"产品验收完成，发布版本 v1.0.0"。

**需要收集的信息**：

1. 迭代目录
2. 验收结论：通过 / 不通过
3. 验收人（**从迭代 README frontmatter 的 `团队成员` 中选择**，写为 `姓名 域账号`；默认取迭代 frontmatter 的「产品负责人」，如不一致需用户确认）
4. 发布产物（制品仓库地址或制品版本号，如 `v1.0.0`、Maven 坐标、镜像 tag）

**执行步骤**：

1. 定位迭代 README.md
2. 在 `## 验收发布` 章节中：
   - 勾选验收结论：`[x] 通过` 或 `[x] 不通过`（另一项保持空）
   - 填写验收人
   - 填写发布产物
3. 写回文件
4. 运行 `schemark valid` 校验

**示例 diff**：

```diff
 ## 验收发布

-验收结论：[ ] 通过 / [ ] 不通过
-验收人：
-发布产物（制品仓库地址或制品版本号）：
+验收结论：[x] 通过 / [ ] 不通过
+验收人：林菲 linfei
+发布产物（制品仓库地址或制品版本号）：v1.0.0
```

**注意事项**：

- 验收不通过时，引导用户在 `## 变更记录` 追加一行说明范围/工期影响，并按情况开新任务或重开缺陷
- 验收通过后通常紧接着归档操作，可主动询问用户是否归档

### 归档迭代

将完成的迭代移动到Sprint工作区内的archive目录。

**前置条件检查**：

1. 迭代目录存在（在Sprint工作区内）
2. 迭代README.md中的"实际结束时间"已填写
3. 建议检查迭代内的任务和缺陷是否都已完成/关闭

**执行步骤**：

1. 确认Sprint工作区内的archive目录存在，不存在则创建
2. 使用`mv`命令移动整个迭代目录到archive下
3. 保持目录名不变

```bash
mv docs/sprint/20260201-20260228-v1.0-支付与订单 docs/sprint/archive/
```

### 分析迭代（Analyze）

通过 `schemark meta` 导出迭代的结构化 JSON 数据，基于数据进行多维度分析。

**触发场景**：用户提到"分析一下这个迭代"、"迭代进度怎么样"、"给我看看任务统计"、"缺陷分布情况"、"迭代报告"。

**执行步骤**：

1. 定位目标迭代目录（同"查找当前Sprint"逻辑）
2. 运行 `schemark meta` 导出 JSON：

```bash
schemark meta docs/sprint/{迭代目录}
```

3. 解析 JSON 输出，按 `type` 字段分类（任务 / 缺陷）
4. 根据用户需求进行分析并输出结论

**JSON 输出结构说明**：

`schemark meta` 输出一个 JSON 数组，每个元素代表一个已解析的文件，包含以下字段：

```json
{
  "path": "相对路径",
  "frontmatter": { /* 文件的 YAML frontmatter 字段 */ },
  "迭代名称": "目录全名",
  "迭代计划开始": "yyyy-MM-dd",
  "迭代计划结束": "yyyy-MM-dd",
  "迭代版本": "vX.X",
  "已归档": false,
  "type": "任务 | 缺陷",
  "id": "T0001 | B0001",
  "标题": "文件标题"
}
```

其中 `frontmatter` 根据文件类型不同而不同：
- 任务：包含 `负责人`、`预估工时`、`已投入工时`、`状态`、`标签`、`关联内容`
- 缺陷：包含 `优先级`、`严重性`、`提出人`、`处理人`、`状态`、`关联任务`、`引起人`、`缺陷起因`、`解决方法` 等

**分析维度**：

根据导出数据，可从以下维度进行分析（根据用户需求选择）：

1. **进度总览** - 任务完成率、缺陷关闭率、整体迭代健康度
2. **工时分析** - 预估 vs 已投入工时对比、工时偏差率、人均负荷
3. **缺陷分析** - 按优先级/严重性分布、按处理人分布、待修复占比
4. **人员负荷** - 每人任务数、缺陷数、工时占比
5. **风险识别** - 逾期风险（已投入 > 预估）、阻塞缺陷（紧急/致命未修复）、人员瓶颈
6. **趋势对比** - 多迭代横向对比（需指定多个迭代目录）

**输出格式**：

以结构化中文分析报告形式直接输出给用户，包含数据摘要和关键结论。不生成文件，直接在对话中呈现。如果用户需要持久化报告，可建议将分析结果保存为迭代目录下的附件。

**多迭代分析**：

如需跨迭代对比，可对多个迭代目录分别执行 `schemark meta`，合并结果后进行横向分析：

```bash
schemark meta docs/sprint/{迭代目录1}
schemark meta docs/sprint/{迭代目录2}
```

也可对整个Sprint工作区执行（包含所有活跃迭代）：

```bash
schemark meta docs/sprint/
```

### 校验

运行schemark命令对Sprint工作区进行结构校验。

**执行时机**：每次创建或修改操作后自动执行

**命令**：

```bash
schemark valid docs/sprint/{当前迭代}
```

**处理结果**：

- 如果校验通过，简单告知用户
- 如果校验失败，展示错误信息并提示用户修复

## 辅助功能

### 自动发现Sprint工作区

使用 `find_schemark.py` 脚本自动定位 `schemark.json` 文件：

```bash
python3 scripts/find_schemark.py <start_dir> [max_depth]
```

**默认查找顺序**：

1. 检查 `docs/sprint/` 是否有 schemark.json
2. 检查当前目录是否有 schemark.json
3. 向上查找父目录（最多3层）
4. 向下查找子目录（最多3层）

**返回值**：

- 成功：输出 schemark.json 所在目录的绝对路径（即Sprint工作区路径）
- 失败：输出错误信息到stderr，退出码1

### 查找当前Sprint

如果用户没有明确指定sprint，需要智能判断：

1. 检查当前工作目录是否在某个sprint目录内
2. 如果在Sprint工作区根目录，使用 `find_sprints.py` 列出所有非archive的sprint目录，选择最新的
3. 询问用户确认

### 编号冲突处理

如果计算出的编号已存在：继续递增直到找到可用编号，警告用户可能存在编号不连续。

### 日期格式转换

用户可能用自然语言描述日期，需要转换为规范格式：

- "明天" → 计算具体日期
- "下周一" → 计算具体日期
- "2026年2月1日" → 20260201
- "2026-02-01" → 20260201

### 人员信息格式

确保人员信息符合"姓名 域账号"格式。如果用户只提供姓名，提示需要域账号。

写入任何人员字段前，先核对该人员是否已在迭代 README frontmatter 的 `团队成员` 列表中：

- 在列表中：直接按列表中的拼写写入 `姓名 域账号`
- 不在列表中：先把新成员追加到 `团队成员`（与用户确认拼写），再写入目标字段；不允许跳过 `团队成员` 直接写新名字

## 错误处理

1. **找不到schemark.json**：
   - 首先检查默认位置 `docs/sprint/`
   - 使用 `find_schemark.py` 在当前目录附近自动查找
   - 如果仍未找到，提示用户尚未初始化Sprint工作区，建议运行初始化操作
   - 引导用户指定Sprint工作区目录进行初始化（默认 `docs/sprint/`）

2. **sprint目录不存在**：提示用户指定的sprint不存在，使用 `find_sprints.py` 列出可用的sprint

3. **必填字段缺失**：明确告知缺少哪些字段，引导用户补充

4. **校验失败**：展示schemark的错误信息，帮助用户理解并修复

## 注意事项

1. **严格遵守schemark.json规范**：所有创建的文件和目录必须符合规范
2. **保持文件格式一致**：frontmatter使用YAML格式，body使用Markdown
3. **编号连续性**：尽量保持T/B编号连续，避免跳号
4. **日期格式统一**：目录名用yyyyMMdd，frontmatter中的日期用yyyy-MM-dd
5. **人员信息格式**：始终使用"姓名 域账号"格式，且必须出自迭代 README frontmatter 的 `团队成员` 列表（详见前文「人员信息一致性规则」）
6. **必须章节**：确保README.md和B文件包含所有必须的章节（迭代 README 的 `## 篝火评审` 章节在创建时就要填入真实评审报告，不能留 TODO 占位；如不适用，由用户确认后填写理由）
7. **校验反馈**：每次操作后运行校验，及时发现问题
8. **用户确认**：对于重要操作（如归档），在执行前确认用户意图
9. **工作区隔离**：所有操作仅在Sprint工作区（默认 `docs/sprint/`）内进行，绝不修改仓库根目录或创建 `.claude/` 等配置目录

## 技能边界

本技能**仅负责**在Sprint工作区内管理迭代文件，**不负责**：

- 修改schemark.json规则定义
- 编辑任务/缺陷的详细内容（只负责创建和状态流转）
- 生成复杂的项目报告
- 与外部系统（如Jira、GitLab）集成
